# 专用 Agent 需求与实现可行性总结

[English](specialized-agent-summary.md) | 中文

> 目的：把「为特定大型工程构建专用 Agent，并能在通用/专用模式间一键切换」
> 这一需求，与 DSH 实际提供的能力对齐，形成可据以决策的文档。
> 依据：本会话对 DSH 的实测（脚本可复现）与官方契约通读。
> **本文不涉及任何具体工程的代码或结构。**

---

## 一、需求陈述

| # | 需求 | 性质 |
|---|---|---|
| R1 | 为特定工程构建专用 Agent 行为 | 能力定制 |
| R2 | **直接修改 harness，而非 skill/rule 软约束** | 硬性约束 |
| R3 | 一键切换【通用模式】与【专用模式】 | 可用性 |
| R4 | 在 DSH Web UI 与桌面客户端上都要可用 | 覆盖面 |
| R5 | 不破坏 DSH 升级能力 | 可维护性 |

---

## 二、结论

**五项需求全部可在当前安装版本（`0.1.5-rc.2`）上满足，无需修改 DSH 本身，无需从源码运行。**

核心判断：**R2 所指的「改 harness」有两层含义，而 DSH 恰好把这两层都设计成了扩展点。**

| 理解 | DSH 对应能力 | 是否需要改 DSH 源码 |
|---|---|---|
| 改**行为**（工具集、persona、策略） | `agent-presets` | **不需要** |
| 改**机制**（agent 循环本身） | 替换 `AgentFactory` + 4 个生命周期钩子 | **不需要**（但工作量大） |
| 改**DSH 自身代码** | 从源码运行 | 需要 |

**推荐落在第一层。** 它是官方为该场景设计的机制，且完全满足 R2 的「硬约束」要求。

## 三、为什么 `agent-presets` 算「硬约束」而非软约束

这是需求与能力对齐的关键点，值得说清楚。

skill / rule 是**提示词层面**的约束 —— 模型可以选择不遵守，工具依然可见可用。

`agent-presets` 是**组合层面**的定义。一个 preset 的 `agent.cordis.yml` 决定：

| 维度 | 表现形式 | 硬度 |
|---|---|---|
| 工具集 | 插件**真挂载或真不挂载** | 硬 |
| persona | 系统提示词**真替换** | 硬 |
| 计划模式 | 策略文本**真注入** | 硬 |
| 压缩策略 | 阈值**真生效** | 硬 |
| 委派能力 | 子代理/工作流**真启用或禁用** | 硬 |
| 指令加载 | 文件与字节上限**真配置** | 硬 |

官方 `standard` preset 的实例证明：它定义了一个包含 persona、shell、文件系统、
后台任务、Skills、计划、压缩、委派共 10 组能力的完整 agent。

**换 preset = 换掉这个 agent 是什么。** 这符合 R2。

## 四、能力与需求对照

| 需求 | DSH 能力 | 实测证据 | 状态 |
|---|---|---|---|
| R1 专用行为 | preset 定义完整组成 | `standard` preset 含 10 组能力 | 满足 |
| R2 硬约束 | 工具真挂载/真不挂载 | 组合对比 152 vs 153 条目 | 满足 |
| R3 一键切换 | `dsh-client-ui-agent-preset` 选择器 | 包已挂载，UI 中可见 | 满足 |
| R4 双端可用 | 桌面端加载同一前端产物 | 152 : 152 零差异 | 满足 |
| R5 不破坏升级 | preset 存于 `<dshHome>/.agent-presets` | 实测：不在 DSH 安装目录内 | 满足 |

### 额外可用的两个维度

| 维度 | 机制 | 管什么 |
|---|---|---|
| 权限 | `permission-presets` | 沙箱模式、审批策略 |
| 组成细节 | patch 的 `insert` / `disable` | 对组合的增删改 |

三者正交，可组合使用。

## 五、基本逻辑：模式如何工作

### 存放结构

```
<dshHome>/.agent-presets/
├── general/                 # 通用模式（或直接用内置 standard）
│   ├── preset.yml
│   └── agent.cordis.yml
└── specialized/             # 专用模式
    ├── preset.yml           # name / description / order
    ├── agent.cordis.yml     # 复制的完整组成，按需编辑
    └── skills/              # 可选：专属 Skills
```

### 显示与切换

`preset.yml` 就是 UI 里显示的两行：

```yaml
name: 专用模式
description: 面向 <工程> 的专用 Agent，启用 X/Y/Z。
order: 10
```

选择器按 `order` 排序，两个模式并排出现，点击即切换。

### 一条关键规则

**只有空会话能切换 preset。**

这不是缺陷，而是设计：preset 决定 agent 组成，中途更换会破坏会话历史的一致性。

**实际交互**：切换模式 = 新建会话并选中目标 preset。

### 制作方式：官方规定「只能复制」

`dsh-agent-presets` 明确要求 *"Authoring is copy-only"* —— 复制一个已有 preset
的整个目录，然后编辑。id 必须是 `[a-z0-9][a-z0-9-]*`，且不能与已有重复。

官方自己也这么做：内置的 `cordis` 与 `code` preset 就是「复制 `standard` 再改」。

## 六、关键取舍

### 取舍 1：复制带来的上游漂移（需要主动管理）

复制 `standard`（255 行）意味着 **DSH 上游对 `standard` 的改进不会自动流入副本**。

| | |
|---|---|
| 官方态度 | 接受。`cordis`/`code` 就这么做的，理由是「整个组装在一个文件里可读」 |
| 风险 | 上游修复/改进不会到达你的专用模式 |
| 建议 | 定期 diff 上游 `standard` 与你的副本，主动决定是否吸收 |

这是**唯一需要持续投入的维护成本**。

### 取舍 2：一个模式还是多个

可以建多个专用 preset（如：专用-完整、专用-只读分析、专用-构建），
共用大部分行，只改关键几项。UI 按 `order` 排列。

**建议**：先做一个，跑一段时间，确有需要再拆。

### 取舍 3：是否需要更深的定制

只有当「工具集 + persona + 策略」的组合仍不足以表达意图时，才需要：

| 更深一层 | 能力 | 代价 |
|---|---|---|
| 生命周期钩子 | 4 个钩子可改写行为 | 写一个插件，中等 |
| 替换 `AgentFactory` | 换掉整个 agent 循环 | 需自实现事务、事件序列、持久化接入，**官方定位为最后手段** |

**建议路径：preset → 钩子 → 替换 factory。** 逐层下沉，每层都不够再往下，
避免预先重写一个驱动。

## 七、已实测的能力边界

以下均经本会话实测（脚本可复现），非推断：

| 能力 | 实测结果 |
|---|---|
| 两个组合共存且互不干扰 | 152 vs 153 条目；loop 参数 `default` vs `2`；专用层独有的条目未泄漏 |
| patch 可到达 loop 配置 | `maxParallelToolCalls: 3` 生效 |
| 整个 agent loop 可替换 | 原生行禁用后，自定义 factory **成功注册** |
| factory 排他性 | 原生在位时注册第二个 → `an agent factory is already registered` |
| 可用的生命周期钩子 | 4 个：`agent/pre-step`、`agent/request`、`agent/request-error`、`agent/turn-stopping` |
| Web 与桌面端对等 | 152 : 152 零差异 |
| preset 选择器存在 | `dsh-client-ui-agent-preset` 已挂载 |

### 尚未验证的部分

**一个功能完整的专用 preset 能否在目标工程上跑通实际任务。**

这需要：真实的工程环境 + 实际的组成设计 + 迭代调优。
本会话按要求未接触工程内容，因此这一层留待需求确认后投入。

## 八、风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| **上游漂移**（取舍 1） | 专用模式逐渐落后于上游改进 | 定期 diff；或把可共享部分保持最小 |
| DSH 是 RC 版本 | 接缝可能变动 | 锁定版本；preset 是**配置文件**而非代码，升级冲击比改源码小得多 |
| 组成设计不佳 | 专用模式反而不如通用模式 | 从复制 `standard` 开始，增量修改，保留可回退性 |
| 模式过多 | UI 混乱、维护分散 | 先做一个，按需拆分 |
| 误以为可以中途切换 | 操作困惑 | 明确：切换 = 新建会话 |

**注意**：使用 preset 方式的最大好处是它**不是代码**。
即便 DSH 升级导致接缝变动，你的专用模式也只是一份 YAML，迁移成本远低于自定义驱动。

## 九、建议的推进顺序

| 阶段 | 内容 | 产出 |
|---|---|---|
| 1 | 复制 `standard` 为专用模式，仅改 `preset.yml` 的名称描述，验证出现在 UI 中 | 可切换的空壳模式 |
| 2 | 逐项调整 `agent.cordis.yml`：先 persona，再工具集，再策略 | 专用行为成型 |
| 3 | 在真实任务上迭代，识别不足 | 调优后的组成 |
| 4 | 若组成仍不足以表达意图，评估生命周期钩子 | 必要时再下沉 |
| 5 | 建立与上游 `standard` 的定期 diff 机制 | 抗漂移 |

阶段 1 是**低风险验证** —— 只改显示名，确认整条链路（文件位置、UI 显示、切换）
畅通后再投入阶段 2 的组成设计。
