# 查询索引性能基准：方法与结论

> 本文记录"为什么查询索引要做成持久化 SQLite、并且禁止在查询路径上构建"的量化依据。原始测量来自一个中大型文本工程（数百个源文件、数十万条记录），具体数据已脱敏，只保留数量级与结论。实现细节见 [`domain-tool-patterns.md`](domain-tool-patterns.md) §8–§9。

## 1. 怎么测

- 脚本放在 `packages/dsh-tool-example/test/`（如需新增基准，命名为 `bench-*.mjs`）。
- **每轮独立进程**（冷启动），依次调用若干个真实工具调用，记录每次耗时与进程峰值堆。
- 对比四组：
  1. 旧实现 + 旧索引（首次调用）
  2. 旧实现 + 旧索引（第二次调用）
  3. 新实现 + **失效**索引（降级为直接扫描源文件）
  4. 新实现 + 新索引
- 构建耗时走设置窗口「重建索引」的同一代码路径（worker 线程），记录总耗时、DB 体积、heap / RSS 峰值。

## 2. 结论（数量级）

| 观察 | 数量级 |
|---|---|
| 旧实现在查询路径里发现索引过期就**同步重建** | 单次调用卡住约 **100 秒级**，期间 agent 完全无响应 |
| 新实现 + 新索引，典型会话总耗时 | 从 **10–100 秒级** 降到 **1–2 秒** |
| 进程峰值内存 | 从 **数百 MB** 降到 **约 100 MB**（不再常驻解析后的整棵源文件树） |
| 反向引用类查询（原本需要全量扫描） | 从 **秒级** 降到 **个位数毫秒** |
| 单个源文件首次读取 | 略增几十 ms（解压 + JSON 解析 + 一次 stat），但文件越大收益越明显 |
| 全量构建 | 约 **分钟级**，DB 体积与源数据同数量级，峰值 RSS 约 1 GB（在 worker 线程内，不影响 UI） |

## 3. 设计决策

- **查询路径从不构建索引**：失效时直接读源文件（结果正确，只是慢），并在回答末尾附提示"到设置里重建索引"。这是消除 100 秒级卡顿的关键。
- **逐文件新鲜度**：用 stat 快指纹判断单个源文件是否改动；改过的文件回退读源文件，其余仍走索引。
- **整体性改动需要重建**：跨文件的派生数据（如反向引用表）无法逐文件判断新鲜度，重建前回答里注明"索引构建时间"。
- **版本常量**：索引结构或构建逻辑一变就递增 `SCHEMA_VERSION` / `BUILDER_VERSION`，旧索引自动判为失效。
- **一致性验证**：任何"索引加速"的查询都要有一个验证脚本，把索引结果与实时扫描结果逐项比对。
