# 落地后续需求：到底需不需要热更？

[English](do-you-need-hot-update.md) | 中文

> 问题：用桌面客户端落地后续需求，实际上是否需要热更能力？
> **直接回答：取决于你在哪个阶段。开发阶段完全不需要热更；已部署阶段才需要。**
> **本文不涉及任何具体工程的代码或结构。**

---

## 直接回答

**分两个阶段，结论相反：**

| 阶段 | 需要热更吗 | 原因 |
|---|---|---|
| **开发阶段**（你在源码目录迭代） | **不需要** | 改完重启应用即可，一次几秒 |
| **已部署阶段**（用户装好之后） | **需要** | 否则每次改动都要重装 |

**所以：如果你现在是"在桌面客户端上开发这套东西"，答案是——不需要热更。**

热更是**分发**问题，不是**开发**问题。

---

## 一、为什么开发阶段不需要热更

### 你的迭代循环

```
改 preset YAML / 改 patch
        ↓
重启应用（Ctrl+Q 后重新启动，或直接 npm start）
        ↓
验证
```

**一次重启几秒钟。** 相比热更机制的实现成本，重启是压倒性划算的。

### 具体到各类改动

| 你要改的东西 | 开发阶段怎么做 | 需要热更吗 |
|---|---|---|
| preset 的 `agent.cordis.yml` | 改完重启 | 否 |
| `cordis.patch.yml` | 改完重启 | 否 |
| 壳层代码（`src/main/*.ts`） | `npm run build` + 重启 | 否 |
| 前端 bundle | 重新构建 + 重启 | 否 |
| DSH 本体 | 无需改 | — |

**在源码环境里，所有东西都"可写"且"重启即生效"，所以热更没有价值。**

### 唯一的不便是重启

而这有几个缓解手段，成本远低于实现热更：

| 手段 | 效果 |
|---|---|
| `npm start` | 一条命令构建 + 启动 |
| 会话持久化 | 重启后历史还在（已实测：数据在数据根里） |
| preset 选择持久化 | `agent-presets.default` 记住选择 |

**注意**：重启丢失的只是"当前正在进行的流式输出"，不是会话历史。

---

## 二、已部署阶段为什么需要热更

用户装好应用后，`resources/` 目录：

- **不是他创建的**，改动不自然
- **升级会被覆盖**（见 `self-maintenance.zh.md`）
- 让用户每次改配置都重装应用，不可接受

**这才是热更的适用场景。**

但即便如此，也**不是所有改动都需要热更**：

| 改动 | 已部署阶段怎么办 | 需要热更吗 |
|---|---|---|
| preset 内容 | 用户直接编辑数据区文件 | **否**（重启即可） |
| 启用/禁用插件 | 编辑 patch 文件 | **否**（重启即可） |
| 装新插件 | `npm install` 到 profile 目录 | **否**（重启即可） |
| 不想重启 | — | **是**（这才是热更的价值） |

**关键**：热更的价值只在于**"不重启"**，而不是"能不能改"。

## 三、我上一轮的话需要修正

我说"专用 agent 不需要 L2/L3/L4"，这句话**在特定范围内**是对的：

| 那句话的准确范围 | |
|---|---|
| 说的是 | **专用 agent 的组成定义与切换**（数据 + 一个 L1 行） |
| 说的是 | **四层能力都已随 DSH 挂载，你不需要实现它们** |
| **没有说** | 内核迭代不需要更新部署的代码 |

**如果内核（DSH 本体）要迭代**，那是另一回事：

```
新 DSH 版本 = 磁盘上换了新代码
           = 已运行进程无法感知（Node 模块已导入并缓存）
           = 必须重启
```

**所以：内核迭代确实需要"更新"，只是那个"更新"是重启，而不是热更。**

---

## 四、三种"更新"要分清

这是最容易混淆的地方：

| 说法 | 实际含义 | 需要什么 |
|---|---|---|
| **不需要热更** | 改动是数据，重启即可 | 重启 |
| **需要更新部署代码** | 换了可执行代码 | 重启（+ 换文件） |
| **需要热更** | 换了代码/数据但**不想重启** | 热更机制 |

**你上一轮问的"内核迭代"落在第二行：需要更新代码，但那个更新是重启。**
**而"热更"特指第三行 —— 不重启。**

---

## 五、给你的实际建议

### 现在（开发阶段）

**不要实现热更。** 直接迭代：

```bash
npm start          # 构建 + 运行
# 改东西
Ctrl+Q 然后 npm start
```

**理由**：热更机制的实现成本（第六节）远高于它在你开发阶段节省的时间。

### 将来（要给用户分发时）

那时再考虑，且按优先级：

| 优先级 | 能力 | 解决什么 |
|---|---|---|
| 1 | profile 移到数据区 | 让用户能改，且升级不覆盖 |
| 2 | 重启按钮 | 改完一键重启（比热更简单得多） |
| 3 | 热更按钮 | 少一次重启 |

**第 2 项是关键** —— 一个"重启应用"按钮能解决 90% 的问题，
而实现成本接近零（`app.relaunch()` 已可用，实测确认）。

**热更（第 3 项）是锦上添花，不是必需品。**

---

## 六、热更的实现成本（为什么建议往后放）

| 组件 | 状态 | 工作量 |
|---|---|---|
| 宿主重新组合 | 已存在 | 0 |
| 渲染进程重载 | 已实测可行 | 小 |
| 检测变化 | 需实现 | 中 |
| 空闲时触发（避免打断流式输出） | 需设计 | 中 |
| 失败回滚 | 需设计 | 中 |
| 用户提示 | 需实现 | 小 |

**而且它只能覆盖"组合与客户端插件"** —— 内核代码改动（L3/L4）依然需要重启。

**即：热更解决不了内核迭代，而内核迭代本来就不常发生。**

---

## 七、回答

> **用桌面客户端落地后续需求，实际上不需要热更？**

**开发阶段：对，不需要。**

**已部署阶段：需要"能改"，但不一定需要"热更"** ——
一个重启按钮就够了，热更只是省掉那几秒。

**而内核迭代是另一回事**：它确实需要更新部署的代码，且必须重启（Node 模块缓存 + L3 阻塞）。
那个"更新"不叫热更，叫"换版本 + 重启"。
